> 2026-07-22). See [README](./README.md).
> Validation: 🔵 Static. HTTP methods and paths were extracted mechanically from the

An **entry point** is where execution begins after an outside event. Reading the code
starts here. There are **five kinds** of entry point in this system:

1. [Process / server startup](#21-process--server-startup)
2. [HTTP API routes — Fab](#22-http-api-routes--fab-claudeai_athena) (40 routes)
3. [HTTP API routes — Admin](#23-http-api-routes--admin-admin_athena) (29 routes)
4. [Page navigations](#24-page-navigations-client-entry-points) (client entry points)
5. [AI-invoked tools](#25-ai-invoked-tools-runtime-dynamic-entry-points) — the AI chooses these at **runtime**

> **Convention:** every `route.ts` file exports one function **per HTTP method**
> (`GET`, `POST`, `PATCH`, `PUT`, `DELETE`). That exported function *is* the entry point.
> Every `page.tsx` default export is a page entry point.

## 2.1 Process / server startup

| Entry point | File | Trigger | Notes |
|-------------|------|---------|-------|
| Next.js standalone server | `server.js` (generated by `next build`, not in source) | Docker container start (`CMD ["node","server.js"]`) | Serves both routes and pages. Port 3000 (Fab) / 3001 (Admin). |
| Startup hook (Admin) | `admin_athena/instrumentation.ts` | Next.js boot | **Intentionally a no-op** — the retention worker can't run here (it imports `pg`). ⚠️ Verify nothing relies on it. |
| Build/runtime config | `claudeai_athena/next.config.ts`, `admin_athena/next.config.ts` | Build + boot | `output: "standalone"`; marks `pg`/adapter as server-external. |

> There is **no** long-running background scheduler wired up. `admin_athena/lib/session-retention-worker.ts` and the various `purge*` functions exist but are **not auto-started** — they must be invoked manually or by an external cron. **This is a known gap to confirm with a code owner.**

## 2.5 AI-invoked tools (runtime-dynamic entry points)

These are the **hardest entry points to document**, and the reason the assignment warns
you may need runtime logs: **the LLM decides at runtime which tool to call.** Static
reading tells you which tools *exist* and what they do; only runtime logs confirm which
actually fires for a given prompt.

| Tool family | Defined in | Invoked by | Notes |
|-------------|-----------|-----------|-------|
| **Fab chat tools** | `chat/route.ts` (assembly) + `lib/mcp-client.ts` | Fab chat AI | `code_execution` (always), `web_search`/`web_fetch` (toggle), + MCP tools loaded from authorized `McpConnection`s |
| **MCP tools** | discovered from remote MCP servers, cached in `mcp_connections.available_tools` | Fab chat AI | Executed via `executeMcpTool` (JSON-RPC over HTTP). The actual tool logic lives in **external MCP servers not in this repo** (see [scope §0.2](./00-phase-0-scope-and-inventory.md#02-scope-reconciliation)). |
| **Modeling-Agent tools (13)** | `lib/chat-cmf/tools.ts` | Modeling Agent AI | e.g. `resolveObjectType`, `getRequiredFields`, `browseCmfRecords`, `fillFromExisting`, `generateExcel`, `validateTemplate`. `previewLoadImpact`/`loadToCmf` exist but are hidden in v1. |
| **Admin chat tools (~30)** | `lib/admin-tools.ts` + `lib/admin-system-prompt.ts` | Admin AI | The real admin API surface: `query_user_sessions`, `query_error_audit`, `mark_error_resolved`, `invite_user`, `add_mcp_to_role`, `update_error_catalog_message`, `purge_old_*`, etc. Each self-logs to `audit_logs`. |

> **Documentation note:** For each AI tool family, the catalog above lists the tools; a
> later scenario (a full prompt turn) will trace *one* concrete tool call end-to-end. The
> complete per-tool inventory (inputs/outputs/side-effects) belongs in the function
> inventory (Phase 2 tables, being generated per-file now).

## 2.6 Which entry points to trace as scenarios (Phase 3)

Ranked by how often managers/customers ask about them and by risk:

1. ✅ **Login** — done ([scenario 01](./scenarios/01-login.md)).
2. **A full chat prompt turn** (`POST /chat`) — auth → RBAC → tools → stream → usage/prompt audit. *Highest value.*
3. **An MCP tool call** — from the AI's decision to `executeMcpTool` to the external server. *Needs runtime logs.*
4. **A CMF master-data load** (`POST /cmf/packages/[id]/load`) — *data-affecting, highest risk.*
5. **An admin action** (e.g. force-logout, or an admin-chat tool that mutates) — with its transactional audit write.
6. **A deployment** — CodeBuild → image → EB (from the deployment docs).
